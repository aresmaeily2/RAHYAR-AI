# اتصال‌های بیرونی — مسیرهای رسمی و شفافیت (بخش‌های ۱۰ و ۱۱ دستور)

> وضعیت نسخه فعلی: **هیچ اتصالی فعال نیست.** کاتالوگ شفافیت در رابط
> («پروفایل و حساب → اتصال‌ها») از `src/lib/connections/catalog.ts` می‌آید.
> فعال‌سازی هر مورد نیازمند: حساب ارائه‌دهنده + مجوز مالک + پیکربندی امن.

## قواعد مشترک همه اتصال‌ها
- توکن فقط در تنظیمات سرور (env/دیتابیس رمزنگاری‌شده) — هرگز در کد کلاینت، URL، لاگ یا گزارش.
- opt-in، حداقلی، قابل لغو؛ مجوز اعلان ≠ مجوز ارسال پیام؛ مجوز خواندن ایمیل ≠ مجوز حذف/ارسال.
- هر اقدام بیرونی: پیش‌نمایش → تأیید کاربر → اجرا → ثبت نتیجه در ActionLog → امکان لغو.

## ۱. ایمیل (Gmail / Outlook)
- مسیر رسمی: OAuth 2.0 + Gmail API با scope `gmail.readonly` (حداقلی) یا Microsoft Graph `Mail.Read`.
- هرگز: IMAP با رمز خام، scope کامل `mail`، حذف/ارسال بدون درخواست صریح.
- منابع روز: developers.google.com/gmail/api — learn.microsoft.com/graph

## ۲. تقویم
- مسیر رسمی: Google Calendar API با scope `calendar.events` (نه `calendar` کامل).
- فقط خواندن + ساخت رویداد با پیش‌نمایش و تأیید برای هر رویداد.

## ۳. تلگرام
- مسیر رسمی: **Telegram Bot API** (`sendMessage`) — ربات فقط به کاربرانی که با آن
  گفتگو شروع کرده‌اند پیام می‌دهد؛ پیام‌دادن به هر کاربر مفروض گرفته نمی‌شود.
- تفاوت مهم: APIهای کلاینت (MTProto) برای اتوماسیون حساب شخصی با ریسک/شرایط
  سرویس متفاوت‌اند — در نسخه فعلی استفاده نمی‌شوند.
- منبع: core.telegram.org/bots/api

## ۴. واتساپ
- مسیر رسمی: **WhatsApp Business Platform (Cloud API)** با قالب‌های تأییدشده متا.
- واقعیت صادقانه: هیچ مسیر رسمی برای دسترسی آزاد به پیام‌های اپ واتساپ شخصی
  وجود ندارد؛ رهیار چنین ادعایی نمی‌کند.
- منبع: developers.facebook.com/docs/whatsapp

## ۵. تماس تلفنی (نسخه اول)
- فقط بازکردن شماره‌گیر (`tel:`) + تأیید کاربر؛ بدون تماس خودکار.

## صفحه رضایت هر اتصال (الزام بخش ۱۱)
هر کارت اتصال این ۶ مورد را نشان می‌دهد:
۱) چه دسترسی‌ای فعال می‌شود ۲) چه داده‌ای جمع می‌شود ۳) داده کجا پردازش می‌شود
۴) آیا به مدل AI می‌رود ۵) چه چیزی ذخیره و تا چه زمانی ۶) چگونه قطع/حذف می‌شود
